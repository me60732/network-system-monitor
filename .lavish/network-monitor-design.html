📋 Open Questions for the Captain

The following questions need resolution before we start building. Click to annotate directly on each card:

Q1: Push vs Pull for systemd service Critical — Resolved ✅

Push model confirmed by Captain. Remote machines send metrics to desktop on a schedule. One-directional UDP protocol — no retries needed, just resend next cycle if packet drops. Also simplifies "discovery" since each remote machine is pre-configured with the host/desktop IP.

Q2: minimon-applet config compatibility — Resolved ✅

Captain confirms: extend the TOML format. We'll review minimon-applet's schema and adapt/extend it rather than creating a new one from scratch.

Q3: Auto-discovery on LAN — Resolved ✅ (Not Needed)

Captain confirms no auto-discovery needed. Each remote machine is pre-configured to point back to the desktop host IP. The only "discovery" that happens naturally: when a new service starts pushing, it includes its machine identifier in the UDP packet, so the desktop automatically picks up newly configured machines.

Q4: Separate binary crate for remote service? — Confirmed ✅

Captain confirms the model. Remote machines only need the systemd service binary. We'll keep `metrics-core` as a shared library crate and have separate binaries for applet (desktop) and nmd-service (remote).

Q5: Install script scope — Firewall deferred ⏭️

Captain confirms keep firewall settings separate as a security precaution. Install scripts will handle cert generation and systemd unit installation only; firewall (ufw) configuration handled manually later.

Q6: ASRock mini readiness — Not Blocking ✅

Captain confirms we don't need the ASRock Mini. We have Pluto (old laptop file server) and Spark set up, plus desktop = three machines for testing. No dependency on ASRock mini.
