Hybrid Cryptography Pairing System

Version 1.0 — Ed25519 + ChaCha20-Poly1305 AEAD

Mission: Replace symmetric HMAC with hybrid asymmetric crypto. Ed25519 for Bluetooth-style pairing (identity + key exchange), ChaCha20-Poly1305 for encrypted + authenticated metrics. Complete security from day 1: per-machine isolation, zero-config, visual approval, confidentiality + integrity.

Current vs New Architecture

❌ Current: HMAC-SHA256 (Symmetric)

  • Shared 32-byte secret at /etc/nmd/secret.key
  • Manual secret distribution (copy to all senders)
  • One compromise = all senders compromised
  • Wire: [rkyv packet with hmac_tag field]
  • 32-byte authentication tag

✅ New: Hybrid (Ed25519 + ChaCha20-Poly1305)

  • Ed25519 keypairs for pairing + ECDH key exchange
  • ChaCha20-Poly1305 AEAD for packet encryption
  • Per-machine security isolation
  • Wire: [encrypted rkyv packet][16-byte Poly1305 tag]
  • Confidentiality + authentication in one operation

Wire Format Changes

Packet Structure

// REMOVE from MetricPacket struct:
pub hmac_tag: [u8; 32],

// Wire format becomes:
[ChaCha20-encrypted rkyv packet][16-byte Poly1305 tag]
              ↑                           ↑
        confidential                  authenticated

// ChaCha20-Poly1305 provides:
// - Encryption (confidentiality)
// - Authentication tag (integrity + authenticity)
// - All in one AEAD operation

AEAD tag is appended after encryption. ChaCha20-Poly1305 encrypts the serialized packet and computes authentication tag in a single operation (faster than separate encrypt + MAC).

Pairing Flow (Trust-On-First-Use)

sequenceDiagram participant S as Sender participant R as Receiver participant U as User Note over S: First Start S->>S: Generate Ed25519 keypair S->>S: Save keypair to disk S->>R: Pairing request with public key Note over R: Unknown sender detected R->>U: Notification: machine wants to connect alt User Accepts U->>R: Click Accept R->>R: Derive shared ChaCha20 key via ECDH R->>R: Store in pairing file R->>S: Pairing accepted S->>S: Derive shared ChaCha20 key Note over S,R: Secure channel established else User Denies U->>R: Click Deny R->>S: Pairing rejected Note over S: Retry later or manual intervention end Note over S: Send Metrics S->>S: Encrypt packet with ChaCha20-Poly1305 S->>R: Encrypted packet with AEAD tag R->>R: Decrypt and verify AEAD tag R->>R: Display metrics

nmd-service/src/udp_sender.rs REFACTOR

Replace HMAC with ChaCha20-Poly1305:

  • Load/generate Ed25519 keypair
  • Derive shared ChaCha20 key via ECDH
  • Encrypt packet with AEAD
  • Append 16-byte Poly1305 tag

cosmic-applet/src/network/udp_receiver.rs REFACTOR

Replace HMAC with AEAD decryption:

  • Split buffer: last 16 bytes = AEAD tag
  • Lookup sender's shared key
  • If unknown → emit pairing request
  • If known → decrypt and verify AEAD

cosmic-applet/src/pairing_manager.rs NEW

Pairing state + shared keys:

  • Load pairing.toml: machine_id → shared_key
  • ECDH key derivation on pairing
  • API: is_paired(), add_pairing(), get_key()
  • Secure storage (0600 permissions)

Security Properties

Property HMAC-SHA256 (Current) Ed25519 (New)
Authentication ✅ Yes ✅ Yes
Integrity ✅ Yes ✅ Yes
Confidentiality ❌ No (plaintext) ✅ Yes (ChaCha20)
Per-machine keys ❌ Shared secret ✅ Unique keypairs
Zero-config senders ❌ Manual key copy ✅ Auto-generate
Compromise isolation ❌ All senders affected ✅ Only one sender
User approval ❌ Silent ✅ Visual notification
Tag size 32 bytes (HMAC) 16 bytes (Poly1305)
Performance ~10μs HMAC ~15μs ChaCha20-Poly1305

Why ChaCha20-Poly1305? Modern AEAD cipher combining encryption + authentication in one operation. Faster than AES-GCM on CPUs without AES-NI. Used by WireGuard, TLS 1.3, SSH. Perfect for our use case: fast, secure, battle-tested.

Testing Strategy

Unit Tests

  • test_keypair_generation() — verify keypair saved with 0600 perms
  • test_signature_roundtrip() — sign + verify succeeds
  • test_invalid_signature() — tampered packet rejected
  • test_unknown_sender() — pairing request emitted

Integration Tests

  • Start sender (fresh keypair) → receiver shows pairing notification
  • Accept pairing → subsequent packets verified
  • Deny pairing → packets dropped
  • Remove pairing → next packet triggers re-pairing

5-Sender Stress Test

  • Update test-5-senders.sh to generate 5 unique keypairs
  • Receiver shows 5 pairing notifications
  • Accept all → all metrics flow correctly
  • Verify no sequence gaps, no packet loss

Migration Path

Breaking Change: Version 1.0 will NOT be compatible with pre-1.0 HMAC senders. This is acceptable for 1.0 release.

For Users Upgrading:

  1. Stop all senders: systemctl stop nmd-service
  2. Update nmd-service and cosmic-applet to v1.0
  3. Delete old HMAC secret: rm /etc/nmd/secret.key
  4. Start senders: systemctl start nmd-service
  5. Senders auto-generate keypairs, receiver shows pairing notifications
  6. Accept each sender via UI notification
